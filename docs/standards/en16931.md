# EN 16931 — the European semantic model

## Scope and version

EN 16931-1 defines the **semantic data model** of the core elements of an electronic invoice: business terms
(`BT-1` … `BT-160`), business groups (`BG-1` … `BG-31`), their cardinalities, and the business rules that
relate them (`BR-*`, `BR-CO-*`, `BR-S-*` …). It is a model, not a file format — two syntax bindings carry it:
UBL 2.1 (EN 16931-3-2) and UN/CEFACT CII D22B (EN 16931-3-3).

Everything in this library is anchored here. The canonical model is the semantic model; every syntax is a
projection of it. When a mapping question has no obvious answer, the semantic model decides.

We target the artefacts published by the Connecting Europe Facility, currently the **1.3.x** line.

intent. Buy the text before designing the canonical model, not before writing a mapping.

## Artefacts

`specs/en16931/` — Schematron for UBL and CII, plus code lists. Fetched by `build/fetch-specs.sh`.

## Model mapping

The canonical `EInvoice` mirrors the semantic model one-to-one, including the business group nesting. Two
consequences:

- Property names follow the standard's vocabulary, not each syntax's vocabulary. `BT-1` is `InvoiceNumber`,
  not `ID` (UBL) nor `ExchangedDocument.ID` (CII).
- Every property carries its business term in its XML documentation, so a developer reading IntelliSense can
  cross-reference the norm.

Code lists that matter and are embedded: UNTDID 1001 (document type), UNTDID 5305 (VAT category), UNTDID 4461
(payment means), UNTDID 7143 (item classification), UNTDID 2379 (date format), ISO 4217 (currency), ISO 3166
(country), EAS and ICD (electronic address and organisation identifier schemes).

## Validation

Two layers, in order:

1. **Syntax** — the XSD of the binding. Structural only.
2. **Semantic** — the EN 16931 Schematron for that binding. This is where `BR-*` rules live.

A CIUS (Factur-X, XRechnung, Peppol BIS, the French CIUS) adds a third layer that may only *restrict*, never
contradict. An Extension may add elements. Rule sets therefore compose, and our validator runs them in that
order, reporting which layers actually ran.

## Pitfalls

- **Rounding and totals.** The `BR-CO-*` rules on VAT breakdown and document totals are where most
  implementations fail. Amounts are decimal with two fractional digits at document level, but unit prices may
  carry more. Never use `double`.
- **The same BT appears in several places.** Some terms are expressed differently by the two bindings; the
  binding standard, not intuition, decides where a term goes.
- **Code list versions drift.** A document valid last year can fail today because a code was retired. This is
  a legitimate diagnostic, not a bug — surface it with the list version in the message.
- **Rules have severities.** Some artefact rules are warnings. A warning is not a failure, and reporting it
  as one makes the library unusable in production.
