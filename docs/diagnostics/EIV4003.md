# EIV4003 — AttachmentTooLarge

| | |
|---|---|
| **Category** | `Safety` |
| **Default severity** | `Warning` |
| **Fallback** | The base64 text is kept in the field's `Raw`; nothing is decoded. |

## What it means

An invoice carried an attachment (BT-125) whose decoded size is over
`DocumentLimits.MaxAttachmentBytes`, 64 MB by default.

The size is judged **before** decoding, from the length of the base64 text: three bytes for every four
characters. Decoding first and measuring after is how a document with a hundred-megabyte payload takes the
process down, and no `catch` recovers from that.

## Example

```
EIV4003  Warning  Safety  An attachment (BT-125) of about 94371840 bytes is over the 67108864 byte limit and
    was not decoded.
    BT-125   found: about 94371840 bytes
    fallback: the base64 text is kept; nothing was decoded
```

## What you still have

The invoice, complete, and the attachment's raw base64 exactly as it arrived:

```csharp
BinaryField attachment = invoice.AdditionalDocuments[0].Attachment;

attachment.Value;      // null — nothing was decoded
attachment.Raw;        // the base64 text, as it appeared
attachment.MimeCode;   // and its declared type and file name
```

Decode it yourself if you have somewhere to put it — a stream to disk rather than a byte array in memory is
usually the right answer for something that size.

## How to change the limit

```csharp
services.AddEInvoicing(o => o.UseLimits(new DocumentLimits { MaxAttachmentBytes = 256L * 1024 * 1024 }));
```

Raise it only for a source you trust. `0` removes the limit entirely, which means an attacker chooses how
much memory your process allocates.
