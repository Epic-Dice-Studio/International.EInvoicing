# EIV1042 — UnknownProfile

| | |
|---|---|
| **Category** | `UnknownProfile` |
| **Default severity** | `Warning` |
| **Fallback** | The nearest registered ancestor profile, down to generic reading of the syntax |

## What it means

The document declares a profile identifier (`BT-24`) that no registered profile matches. The document was
still parsed, using the closest profile available, and this diagnostic records the downgrade.

## Example

```xml
<ram:GuidelineSpecifiedDocumentContextParameter>
  <ram:ID>urn:acme:profile:2p0</ram:ID>
</ram:GuidelineSpecifiedDocumentContextParameter>
```

```
EIV1042  Warning  UnknownProfile  at /rsm:CrossIndustryInvoice/rsm:ExchangedDocumentContext (BT-24)
    expected  a registered profile identifier
    found     urn:acme:profile:2p0
    fallback  parsed as generic EN 16931 CII
```

## What was and was not done

The syntax was read normally, so all EN 16931 business terms are populated. What did **not** happen: the
profile's own rules were not applied, and elements specific to it were kept in `ExtensionData` rather than
mapped. `ValidationReport.IsComplete` is false for this document.

## How to fix it

Either register the profile — it is a supported scenario, see `docs/recipes/add-a-profile.md`:

```csharp
services.AddEInvoicing(o => o.AddProfile(new AcmeProfile("urn:acme:profile:2p0")));
```

Or, if the identifier is simply wrong, have the sender correct it.

## Changing its severity

```csharp
// Refuse documents whose profile you do not know.
services.AddEInvoicing(o => o.OnCode("EIV1042", DiagnosticAction.Fail));

// Or accept them silently, if you deliberately handle only the EN 16931 core.
services.AddEInvoicing(o => o.OnCode("EIV1042", DiagnosticAction.Suppress));
```
