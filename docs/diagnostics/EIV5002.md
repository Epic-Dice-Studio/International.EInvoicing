# EIV5002 — DeclaredEncodingMismatch

| | |
|---|---|
| **Category** | `Safety` |
| **Default severity** | `Warning` |
| **Fallback** | The document is decoded as ISO-8859-1, in which every byte sequence is valid. |

## What it means

The document declares one encoding in its XML declaration and its bytes are not valid in that encoding — in
practice, almost always `encoding="UTF-8"` on bytes that are Latin-1.

This is the single most discussed issue in the German validator's tracker, and it is not exotic. It comes from
a sending system whose database is Latin-1 and whose template says UTF-8, and it is invisible until somebody
looks at a name.

## Example

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Invoice …>
  <cbc:Name>Müller</cbc:Name>   <!-- transmitted as the single byte 0xFC, not as 0xC3 0xBC -->
```

```
EIV5002  Warning  Safety  The document declares encoding 'UTF-8' but byte 431 is not valid in it.
    expected: UTF-8   found: bytes that are not valid UTF-8
    fallback: decoded as ISO-8859-1, in which every byte sequence is valid
```

Had the document been decoded as UTF-8 regardless, `Müller` would have arrived as `M?ller` — a document that
validates, arrives, and is wrong in the one field a human reads.

## Common causes

| What happened | What to do |
|---|---|
| The sender's system writes Latin-1 and its template says UTF-8 | Tell them. Meanwhile the fallback is almost certainly right. |
| A file was re-saved by an editor that changed the encoding but not the declaration | Re-export it |
| The document is genuinely in Windows-1252 | See [EIV5003](EIV5003.md): the two differ only in the range `0x80`–`0x9F` |

## How to handle it

The document is produced, so most callers can log this and carry on. Escalate it if a mis-decoded name is
worse for you than a rejected invoice:

```csharp
services.AddEInvoicing(o => o.OnCode("EIV5002", DiagnosticAction.Escalate));
```

## What is not promised

The fallback is a guess, and a defensible one — ISO-8859-1 accepts every byte sequence, and is what the
senders who get this wrong are usually sending. It is not detection. If the bytes are in some other
single-byte encoding, characters above `0x7F` will be wrong, and the `Raw` of every field still holds exactly
what was decoded, not what was transmitted.
