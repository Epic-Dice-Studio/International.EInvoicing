# EIV4011 — MetadataDisagrees

| | |
|---|---|
| **Category** | `Container` |
| **Default severity** | `Warning` |
| **Fallback** | The embedded XML is used. It is the invoice; the metadata is what the container says *about* it. |

## What it means

A hybrid PDF says two things about itself. The XML inside it is the invoice; the **XMP metadata** wrapped
around it repeats the profile and the name of the embedded file, so that a reader can tell what it is holding
without opening it. This diagnostic fires when the two disagree.

Two disagreements are reported:

| | |
|---|---|
| **the profile is** | The XMP claims one conformance level — `MINIMUM`, `BASIC WL`, `BASIC`, `EN 16931`, `EXTENDED`, `XRECHNUNG` — and BT-24 inside the XML declares another profile. |
| **the embedded file is called** | The XMP names a file the PDF does not carry under that name. |

It matters because both readers exist. A receiver that trusts the metadata and a receiver that opens the XML
then hold different documents, and each is confident. Nothing else in the chain notices: no Schematron rule
looks at a PDF, and neither does a schema.

## Example

```
EIV4011  Warning  Container  The PDF's metadata says the profile is 'EN 16931',
    and the invoice inside it says 'MINIMUM'.
    expected  MINIMUM
    found     EN 16931
```

A MINIMUM document is not an invoice under EN 16931 — it carries header data and totals but no lines. A
receiver that read only the metadata would have accepted it as a full invoice.

## What to check

| | |
|---|---|
| The producer builds the PDF once and the XML separately | The usual cause: a template writes the XMP with a fixed profile while the payload varies. The XML is what the receiver is judged on. |
| The file was assembled by hand, or by two tools | Attaching the XML with one library and stamping the metadata with another is how the names drift apart. |
| The document was converted between profiles | Converting the payload without rewriting the XMP leaves the old claim in place. |
| You are the sender | `International.EInvoicing.FacturX.PdfSharp` writes both from the same profile, so this cannot happen through it. A profile Factur-X publishes no conformance level for is refused at write time rather than stamped with a guess. |

## Handling it

The invoice is usable — the XML was read. Treat this as a signal about the sender rather than about the
document:

```csharp
DocumentResult result = library.Read(pdf);

if (result.Diagnostics.Any(diagnostic => diagnostic.Code == "EIV4011"))
{
    // The payload is what matters, and it was read. Tell the sender their container is lying.
}
```

## What is not checked here

Whether the PDF is a conformant PDF/A-3 at all. That is a specification of its own with a reference
implementation — [veraPDF](https://verapdf.org/) — and this library does not attempt it. See
[the roadmap](../roadmap.md) under *Not doing, on purpose*.

## Both serialisations are read

XMP writes a simple property either as a child element or as an attribute of the `rdf:Description`, and both
are in circulation — Adobe's own tooling writes the attribute form. Both are read here. Reading only the
element form made a container that used attributes look like one saying nothing about an invoice, so a block
claiming the wrong profile passed unremarked, which is the one thing this check exists to stop.
